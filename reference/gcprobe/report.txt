E6 GC-CRASH PROBE (F6) - REPORT
Date: 2026-10-13. Machine: aarch64 Linux VM on Apple silicon, 4 cores, 7.7 GB, 1 Julia thread,
1 GC thread. All paths are relative to scratchpad/phase3/gcprobe unless absolute.

VERDICT
- Reproduced: yes. bbR4.jl aborts 3/3 on 1.12.5 and 3/3 on 1.13.1. The data files cannot be
  read on 1.10.12 (serialization format 30 > 24), but the rebuilt workload runs cleanly on 1.10 (3/3).
- Root cause: a Julia compiler bug (1.12 and 1.13), not the slice and not deserialization.
  JuliaLICM hoists the box of a union phi out of a loop, and the box's field store carries no
  write barrier. A 20-line program without packages reproduces it (repro_upstream.jl).
- Package: no sign that EnzymeRates hits it. Its derivation and identify workloads hoist zero
  allocations on 1.12.5 and 1.13.1, and the stress runs finish without error.
- Recommendation: proceed with phase 3, with a mitigation (see the end).

3. ROOT CAUSE (goal 3)
Observed in the LLVM IR of the smallest crashing caller (gc6.jl main_b; dumps in
logs/ir_mainb.log, logs/ir_mainb_unopt.log, logs/ir_mainb_licm_window.txt):
 a. In the loop, `law(m)` returns Union{Law{Int}, Law{BigInt}}. `L.D` is union-split, and
    the phi of the two results has type Union{Poly{Int}, Poly{BigInt}}. Codegen boxes each
    Poly with julia.gc_alloc_obj plus an 8-byte llvm.memcpy of the `terms` pointer, inside
    the loop body. The unoptimized IR is correct.
 b. InstCombine (the first instance in the -O2 pipeline) turns that memcpy into
    `load i64` + `store i64`. The GC pointer now travels as an integer.
 c. JuliaLICMPass (src/llvm-julia-licm.cpp, v1.12.5) moves both box allocations into the
    loop preheader and adds a memset. Its escape analysis (src/llvm-alloc-helpers.cpp)
    counts `store i64` as a "bits" store, so refstore = 0, and the pass's only guard against
    reference stores never fires. The remark dump shows the contradiction on one field:
    hasobjref: 1 and refload: 1, yet refstore: 0 (logs/remarks_mini5.log, remarks_repro.log).
 d. The hoisted box now lives across iterations and safepoints and becomes old. Each
    iteration writes a fresh, young `terms` Dict into it with no write barrier. The GC frees
    the Dict while the old box still points to it. The next full mark follows the box to
    the freed cell and aborts. The never-written Poly{BigInt} box holds terms = 0, which is
    the "Poly{BigInt}(terms=#<null>)" in the dump.
Inferred, not traced in the GC source: in the no-churn reproducer, GC.gc(true) collects
twice ("GC: 2"). The first pass skips the old, unremembered box and sweeps the Dict; the
second pass marks the box and finds the freed cell.

Why the earlier clues pointed elsewhere: the trigger is the caller's loop in the probe
scripts (bbR4's `L = S.rate_law(m); nD = ... L.D`), fed by the slice API's Union return of
Law{Int} and Law{BigInt}. solve and bare_law return concrete types, so they never trigger
it. Deserialization and the rows only shifted GC timing; the crash outlived both.

Remark scan of the original workloads (hoistscan.py on JuliaLICM remarks):
  bbR4.jl: 4 hoisted allocations, all 4 with a bits store into a reference field.
  gc6 main_b: 2 of 2. repro_upstream.jl: 2 of 2.

Upstream: no matching issue found in a quick web search. #59547 (1.12 regression, write
barrier dropped for a memoryref store; fixed by #59559) is related but uses a different
mechanism. I did not check which 1.12.x first ships that fix. Draft issue text:
upstream_issue_draft.txt; reproducer: repro_upstream.jl. Not filed.

immutable struct with reference fields, drawn from two or more types, that must be boxed.

5. x86 (goal 5)
An x86 run is not needed for the root cause: every step is a target-independent IR pass
(codegen boxing, InstCombine, JuliaLICM), and the aarch64 IR shows each step. It would help
the upstream report, since maintainers will try x86 first, and it would confirm that CI
(ubuntu x64, Julia 1.13) can hit the bug.
Script: repro_upstream.jl (no packages). Workflow: x86_gcprobe_workflow.yml (not committed
anywhere). It runs on ubuntu-latest for Julia 1.10.12, 1.12.5 and 1.13.1:
  for r in 1 2 3; do julia --startup-file=no gcprobe/repro_upstream.jl > run$r.log 2>&1; echo "run $r exit $?"; done
  JULIA_LLVM_ARGS="-pass-remarks=julia-licm -pass-remarks-analysis=julia-licm" \
    julia --startup-file=no gcprobe/repro_upstream.jl > remarks.log 2>&1; python3 gcprobe/hoistscan.py remarks.log
Expected if the bug is target-independent: exit 134 with "GC error" on 1.12 and 1.13,
exit 0 on 1.10, and "hoisted with a bits store into a reference field: 2".

6. RECOMMENDATION FOR PHASE 3: proceed, with a mitigation
- Deserialization is not at fault. Workers that read mechanisms back carry no extra risk.
- Do not let a public or hot-loop API return a Union of parametric immutable structs that
  hold references (the slice's Union{Law{Int}, Law{BigInt}} from checked-Int-then-BigInt).
  Return one concrete type, for example by widening the Int result to the BigInt type at
  the boundary, or keep the retry behind a function barrier whose callers never read fields
  of the union in a loop.
- The EnzymeMechanism{Sig} integer-tuple encoding is not implicated: the bug concerns
  runtime values boxed in loops, not type parameters.
- Add a cheap guard to CI on 1.12/1.13: run a representative workload under the remark
  flags with --pkgimages=no and fail when hoistscan.py reports any "bits store into a
  reference field". About 1-2 minutes per workload here.
- File the upstream issue (draft ready) once Denis approves.
