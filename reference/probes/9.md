# P7 report: codegen IR for a factored rate-law body

## Question
Can a smaller, factored generated body keep `rate_equation` allocation-free and under 120 ns while cutting compile time and native code? I also checked two side questions:
- Does compiled code get shared automatically between mechanisms whose positional laws are identical?
- How often do distinct mechanisms produce identical positional laws?

## Results
**Correctness.**
- Factored laws match the package's polynomials exactly on all 806 plain mechanisms, after dependent substitution, for every factoring option.
- All 2799 mechanisms agree with the package's Reduced `v` within 7.9e-14.
- The Haldane factor H = ΠS − ΠP/Keq divides every numerator, giving a positive quotient: 806 of 806 plain laws, and 1993 of 1993 MWC numerators.
- No term in any of the 8397 laws has a negative concentration exponent.
- All 1527 evaluations with zero concentrations were finite and exact.

**Measurement set.** 102 mechanisms:
- all 42 specs (31 plain, 11 allosteric);
- the 30 init_bibi mechanisms with the most denominator terms (191 down to 83);
- the 30 largest of expand_bibi (396 down to 148; 29 plain plus `expand_bibi/632`, which is allosteric).

**Protocols.**
- T1 is the package's performance-test protocol: minimum over 5 batches of 10,000 calls.
- T2 is a 1000-row loop with fixed parameters.
- Compile time and JIT bytes are deltas around the first call.
- Each variant ran in a fresh process. The kernels were salted so no two mechanisms shared one.

## Verdict
**PASS**, with the body shape stated precisely. Every variant had zero allocations on 102 of 102 mechanisms. segh's maximum is 41.5 ns against the package's 120.8 ns. On large laws, segh cuts compile time 78% and native code 65%.

The gain comes mostly from Horner emission:
- flath alone gets about 70% of it.
- The Haldane factor and the RE-segment nodes add about 20–25% runtime on top.
- Block decomposition adds nothing: segh and facth produce the same code size.
- Factoring without Horner (fact) is worse than flat on the all-SS family: 626, 642 and 658 run 137–141 ns, and their typed statements grow from 4762 to 5722–5803.

## Design implications
1. **Body shape:**
   - load parameters and concentrations positionally;
   - compute each dependent once;
   - compute each needed reciprocal once, so no term divides;
   - make node locals for H, for σ_g and D_g of each RE segment, and for the MWC state, regulatory-site and cross-weight nodes, each shared between numerator and denominator;
   - emit each node by greedy Horner using binary `+` and `*` only;
   - write integer powers as products, never `^`;
   - return `E_total·num/den`.
2. **IR:** the positional law struct above, produced once by the derivation. Leave blocks out (in line with P1). Dividing out dead-end factors exactly helps only 39 of 806 laws, so drop it.
3. **Law in a type or not:**
   - Do not put the law in a type for the sake of sharing. Sharing is rare, a type costs about 17 KB median and up to 80 KB, and it prints as an enormous type in stack traces.
   - If the type is wanted anyway, encode it as one homogeneous Int16 or Int32 tuple and decode by splatting.
   - Never use nested heterogeneous tuples (see Surprises).
4. **AllParameters** has no Haldane factor, so it gets Horner only, at about 0.31× the package's runtime.
5. **Horner is independent of the redesign.** It could replace `_poly_to_expr`'s flat sum today in about 15 lines.

## Open questions for Denis
1. Should the derived law live in a type (pure generator, kernels shared at 0–6% of mechanisms), or should the mechanism stay the only type parameter, with codegen running from a memoized derived IR? I recommend the latter.
2. Should Horner emission go into the current package now, as its own small PR?
3. A later fitter-API decision: a two-phase evaluation that computes parameter-only coefficients once per parameter vector and evaluates only concentration monomials per row (65 + 17 on the largest law).

## Surprises and failures
- **The first type encoding failed.** It used nested heterogeneous tuples. The generator then recompiled its helpers for every law (0.25–0.66 s each) and took 49 s of inference on one 396-term node. My first smoke run hung behind buffered output and had to be killed.
- **Decoding a big tuple by index through dynamic dispatch is slow.** It boxes the tuple on every call: 65 ms per decode. Splatting takes 0.1 ms.
- **After kinetic-group renaming, per-root tree sums lose merges.** On 626 the factored denominator has 577 terms against 396 merged (merged coefficients run 2–8). Without Horner the factored form is slower there. With Horner it is still faster, because the independent nodes run in parallel.
- **The package already exceeds 120 ns on this machine on `expand_bibi/642`** (120.8 ns). The test gate does not cover that mechanism.
- **The Haldane factor improves accuracy near equilibrium only about 2×.**
- **Timings of tiny kernels are noisy to about ±10 ns.** For example, spec 5 measured 16.5 ns flat and 5.1 ns flatr for the same polynomial. Each variant ran once; the 3–4× effects hold consistently across the 60 large laws.
- No Julia process is left running.
